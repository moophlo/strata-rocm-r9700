# DeepSeek 512K context verification

19 November 2026, Asia/Dubai; execution began on 18 November UTC.

## Scope

Increase the total context window from 262,144 to **524,288 tokens**, retaining
the accepted DeepSeek tuning. The manifest persists `CONTEXT=524288`; the
launcher writes the corresponding native `--max-context` and saved preset.

Unchanged: DeepSeek-V4.1-Flash-1017 IQ2_XXS / IST-DAS 2.00 bpw, pinned image
`sha256:50eec886099238f349625b718192fbeeb38abc3e77a36311e24b54d38f0201cf`,
engine `0.1.59-linux-x86_64-hip-rx9070`, R9700, vision, five-expert Faster mode,
CPU request/limit 4/32 with 24 selected physical-core workers, RAM request/limit
32Gi/54Gi, and `ssd-cache=44 dspark=on dspark-block=2 dspark-conf=0.65`.
Turbo Boost stays disabled.

The installed pack declares `max_position_embeddings 1048576`. The pinned
[upstream documentation](https://github.com/Niko1221/Strata/blob/d2f096475817d4666c364c820b0ca830f751cfc5/docs/DEEPSEEK41.md#install)
offers 512K and 1M but explicitly says upstream has not tested beyond 256K.
This local experiment does not establish general reliability at every length.

## Short requests before and after

Identical 65-token coding request, temperature zero, thinking disabled, output
budget 256, two sequential requests per configuration. Outputs reached the
fixed budget; these are throughput samples rather than complete-code checks.

| Total context | Request | Decode tokens/s | First token, s | Cached input tokens |
| --- | --- | ---: | ---: | ---: |
| 262144 | first | 16.1 | 3.888 | 0 |
| 262144 | repeat | 17.2 | 0.160 | 64 |
| 524288 | first | 14.6 | 2.677 | 0 |
| 524288 | repeat | 22.7 | 0.115 | 64 |

The small sample, varying output and cache state do not support a throughput
improvement claim. The purpose is a capacity increase while checking that short
inference and prefix reuse still work.

## Near-capacity retrieval and reuse

The fixture contains 19,362 synthetic maintenance records, three authoritative
verification codes at 10%, 50% and 95%, and a final request to return the codes
as JSON. Its input was sized with the installed model's actual tokenizer and
chat template: **519,979 tokens**, 99.18% of the window. The API reported the
same count. Output budget 128; actual output 33; combined usage 520,012.

| Measurement | Cold request | Identical repeat |
| --- | ---: | ---: |
| Correct verification codes | 3/3 | 3/3 |
| Cached input tokens | 0 | 519978 |
| Newly read input tokens | 519979 | 1 |
| Native prefill, s | 684.5422 | 0.4209 |
| First token, s | 685.476 | 1.347 |
| Whole response, s | 688.354 | 3.479 |
| Decode tokens/s | 11.5 | 15.5 |
| Drafts offered / accepted | 22/22 | 22/22 |

These decode figures are from short 33-token retrieval answers, not a sustained
generation benchmark. The long initial prefill is a practical cost even though
the context fits and the repeat uses the cache correctly.

## Gateway and OpenCode

The preferred LiteLLM `coding` route is `openai/deepseek-v4.1-flash`, order 1.
Its Helm value `proxy_config.model_list[6].model_info.max_input_tokens`
changes from 262144 to 524288. Server-side dry-run of the existing chart 1.82.3
showed changes only to `litellm-config` and the gateway Deployment's config
checksum; Secret and database resources were identical. The same chart and
locked dependencies are retained; the upgrade skips migration hooks because
the application and schema versions are unchanged. Helm revision 61 deployed
the context metadata change.

The first public replay failed with **HTTP 413**, before inference: its body is
1,956,103 bytes, and the `ai.mufloland.it` Ingress had no explicit body-size
override. The Strata Ingress already allowed 100 MB. Helm revision **62** adds
only `ingress.annotations.nginx.ingress.kubernetes.io/proxy-body-size=16m`.
A server-side dry-run verified that this second update changed only the LiteLLM
Ingress; it did not restart the gateway pods again. The initial failed attempt
is preserved as `gateway-capacity-413.json`.

OpenCode is now 2.3.2. Its live catalog previously assigned `coding` a fallback
200,000-token context and 32,000-token output budget. The existing model entry
in `~/.config/opencode/opencode.jsonc` receives only `limit.context=524288`.
The alias, default model, capabilities, output budget and other user settings
are preserved. OpenCode normalizes this existing V1-style configuration for V2.
Its live model catalog confirmed `limit.context=524288` and `limit.output=32000`
after the edit, without a forced server restart.

After the body-limit fix, the same request through
`https://ai.mufloland.it/v1/chat/completions`, model **coding**, passed:

| Public check | Result |
| --- | --- |
| Prompt tokens | 519979 |
| Correct codes | 3/3 |
| Cached tokens | 519978 |
| Whole streamed response | 11.470 s |
| First content through gateway | 9.989 s |

A subsequent conversation turn included the assistant's answer and asked for
the BETA code. It answered correctly through the same public alias with
**520,027 input tokens**, **520,012 cached tokens**, and **15 newly read tokens**;
total elapsed time was **6.596 s**. These public timings include upload, gateway
and network overhead. Native prefill for the continuation was 0.8908 s. Its
6-token output is too short to establish sustained generation throughput.
